## 三、🔴 P1（结论级）：错解 C 不是「两两相容 ⇒ 可同批」，它是按开始贪心换了计数器

### 3.1 教案说错解 C 是什么

教案 §3.2 的叙述链条非常清楚：

> ① 建相容图，求最大权独立集（**单班组下完全正确**）
> ② 把「两两不重叠」当成「可以同时开工」
> ③ 把「并行」简化为「条数 ≤ K」
> → 于是错解 C 账面 128，真实并发 10，超限 2.5 倍

这个故事很漂亮，而且是本讲的核心卖点（MOC 第 120 行、commit message、README 一句话结论全都在讲它）。

### 3.2 代码里实际写的是什么

我把两个函数体逐行 diff 了一遍，**除了函数名、注释和下面这一行，其余完全相同**：

```python
# greedy_by_start_with_crews（"正确的"按开始贪心，79 分）
if (prof[it[1]:it[2]] + it[4]).max() <= crews:
    prof[it[1]:it[2]] += it[4]        # ← 按"所需班组数"扣容量

# pooled_parallel_greedy（"错解 C"，128 分）
if prof[it[1]:it[2]].max() < crews:
    prof[it[1]:it[2]] += 1            # ← 按"条数"扣容量
```

**就这一个字符。** 没有相容图，没有独立集，没有两两配对，没有「同批」，`wrong_pairwise_pool_formulation()`——那个看起来像是错解 C 核心的函数——**定义了但从未被调用**（我搜过全文，零调用点）。

所以错解 C 的 128 **不是「另一个问题」的解**，而是**同一个贪心、同一个可行域检查、只是把容量单位从「人」换成了「条」**。它当然不可行，任何看过 §2.2 公式 $\sum r_i x_i \le K$ 的人都会立刻同意。**但这不是教案许诺的那个教学点。**

### 3.3 为什么这个区别很要紧

| | 教案说的错解 C | 代码实际的「错解 C」 |
|---|---|---|
| 错误发生在哪 | 建模阶段（相容图上做独立集 → 误以为可并行） | 实现阶段（容量单位写错） |
| 学生能学到 | **区间图的独立集 ≠ 并行集**，多资源下要换模型 | 检查 `r_i` 不要写成 1 |
| 这个错误有多常见 | 很高——这是建模课最容易犯的「类比迁移」错 | 中等——学过约束规划的很少写错 |
| 需要什么工具才能发现 | 必须回到原约束 `Σ r_i x_i ≤ K` | 同样，但更机械 |
| 对应的真实故事 | 「看起来无害的简化」 | 「手滑」 |

教案标题写的是**「同一条不重叠约束写两行还是三行，是两个问题」**——这句话本身是**正确且有价值**的（$\sum x_i + x_j \le 1$ vs $\sum r_i x_i \le K$ 确实是两个模型），但代码里从来没有构造出「写了一行/两行、以为它等价于三行」的那个错误实例。**它构造的是一个「写了三行但把 $r_i$ 全当成 1」的例子——那是三行写对了但系数填错了，不是两行三行的问题。**

顺带修正一个数字：教案说错解 C「比精确解 86 高 49%」——对的（+48.8%）。但它同时说「比按开始贪心 …」，如果读者以为 128 是相对 79 的「另一个问题」，那 128 − 79 = 49 是**绝对差值**，不是百分比（百分比是 +62%）。教案把「+49」和「49%」混用了，**两个 49 是巧合，但含义不同**，容易误导。

### 3.4 怎么修（成本约 30 分钟，收益很大）

**不要删掉现在这个「错解 C」——它其实是个好例子，只是名字挂错了。** 建议改成三个错解，各错一处，正好三层递进：

| 编号 | 名称 | 改一行就能写出来 | 账面 | 真实并发 | 教学点 |
|---|---|---|---|---|---|
| A | 按开始时间贪心、按人数扣容量 | （就是现在的 79） | 79 | 4 ✅ | 可行但次优 |
| B | 按开始时间贪心、**按条数**扣容量 | `+= it[4]` → `+= 1` | 128 | 10 ❌ | **容量单位写错**（现在的「错解 C」） |
| C | **相容图独立集 → 误以为可同批** | 需要真写：求最大权独立集，然后把独立集里的作业**全部放在同一时刻开工** | ~? | 必超 | **建模错位**（教案真正想讲的） |

B 保留（它证明「不可行方案的收益不能比大小」），但要把它的名字从「错解 C」改成「错解 B：容量单位写错」。真正的 C 需要 20 行代码：`max_weight_independent_set(interval_graph)` 之后把结果丢进一个时间槽，然后一算并发就炸。**只有这样，教案 §3.2 那张「三步偷懒」表才对应得上代码。**

如果时间不够，**退一步也行**：把教案 §3.2 的标题从「两两相容 ⇒ 可同批」改成「容量单位：条 vs 人」，并把 `wrong_pairwise_pool_formulation()` 这个死函数删掉——**现在这个函数是代码里的一个谎言，它声明了一个从未发生的错误。**

## 五、🟡 P3：教案的单位写错了——「66 班组·小时」实际是 66 作业·小时

教案 §2.1、README、Teaching_Plan 三处都写：

> 总工时 132 个半小时 = 66 班组·小时

我算了一遍：

- $\sum (\text{止} - \text{起}) = 132$ tick = **66.0 小时** —— 这是**「作业·小时」**（36 条作业各占多少时间之和）
- $\sum (\text{止} - \text{起}) \times r_i = 265$ tick = **132.5 班组·小时** —— 这才是**「班组·小时」**

**两者差 2 倍。** 而 4 支班组 × 13 h（06:00–19:00，HORIZON=18 tick）= 52 班组·小时 —— 等等，这个数比 132.5 小得多，正好对应教案说的「需求峰值 26 支班组，4 支完全扛不住」。**如果按 66 班组·小时算，4 支 × 13 h = 52，只差 27%，看起来「加加班就干完了」；按真实的 132.5 算，缺口是 2.5 倍，才是「只能选一部分做」。** 单位错在这里不是笔记本上的错字，**它把本讲的整个「为什么必须放弃作业」的动机从 2.5 倍缩成了 1.27 倍**。

**建议**：改成「总工时 132 个半小时 = **66 作业·小时 = 132.5 班组·小时**」，并把 52 那个可用容量一起写出来做对照。三处同改。

## 十一、给下一讲的建议

**昨天建议的 Day68「sum 与 max 的分野」，今天被换成了区间调度。** 这个替换本身是对的——它补了真空白，而且 Day67 的资料还没整理到位。但现在有两条路：

**路线 A（推荐）：Day69 讲「怎么检查自己讲的故事是不是真的」。**

不写新模型，就拿 Day66 / Day67 / Day68 三讲当教材：
- Day66：数字对，因果说反了（5 块比 4 块「便宜」→ 其实是块数惩罚项写错）
- Day67：数字对，死刑理由错（实例退化 → 目标函数选型）
- Day68：数字全对，错解 C 名不副实（两两相容 → 容量单位）

三讲三种「故事错法」，共同点是**都不影响程序运行**。教学点：**模型的可信度不由「跑通了」决定，由「每个数字能不能指回一句话」决定。** 这一讲零代码主体、零新场景、纯方法论，而且**它是你现在唯一真正缺的能力**——61 讲教案里没有一讲在教「怎么验证自己的解释」。

**路线 B：Day69 讲「区间调度的对偶」**——把 Day68 的口径 C 写成 LP，看 $\sum r_i x_i \le K$ 的影子价格，验证「瓶颈是窗口不是人」这句话。技术上顺，但**它是第 62 讲库存，而消费还是 1**。

我倾向前者。**因为前者的产出你能直接用，后者的产出只能进索引。**
