## 一句话结论

**「试」是要花钱的，而且价码随结构变：400 炉里，纯贪心（只热身一次）亏掉 21 炉，ε-贪心 13.7 炉，
教材默认的 UCB（c=1）反而亏掉 45 炉——因为它把 1/4 的炉次用在三流工艺上；
把 c 调到 0.25 才回到 16 炉。而 Thompson 用先验自动把「还敢不敢试」算清楚。
同时，UCT 用在「4 户 8 批共用 1 间烤房」这种带先后约束的排产上，**只会收敛到一个「规整解」**（把一家的两批连着烘完），
比最好的静态规则差 43.8%；这类问题本来就不该给 UCT：81 个状态的 DP 一步到位。**

## 十问

1. **谁在决策？** 县烟叶站（选烘烤工艺、排烤房）+ 4 户烟农（谁家的烟先上炉）。
2. **决策是什么？** ① 每炉用 6 种工艺中的哪一种（按过去的达标记录在线学）；② 共用烤房每炉烘谁家的哪一批。
3. **不做的代价？** 工艺选错 = 整炉降级/报废；排错顺序 = 烟叶在屋里多放一天掉一档，损耗按「担 × 等待天数」计。
4. **数据从哪来？** 6 种工艺的历史达标率（内部记录，**这一季的烟叶品质不同，真值未知**）、各户各批的担数与烘制天数（收购台账）。
5. **量化目标？** ① 400 炉的累积 regret（相对「全知全能」少收的达标炉数）；② 总加权等待（担·天）。
6. **可行域？** ① 每炉必须选一种工艺，被选的工艺产出一个 0/1 结果；② 每家两批必须先后上、每次只烘一批。
7. **对照方案？** 纯贪心/ε-贪心/UCB(c=1, 0.25)/Thompson；静态调度规则（最短批优先/最大批优先/担数时长比）+ UCT（两套选枝口径 × 5 个模拟量）。
8. **敏感什么？** **结构**（冠军领先 8 个点 vs 只领先 2 个点）、UCB 的 c、UCT 的模拟量与选枝口径、rollout 设计。
9. **结论对谁有用？** 站长（要不要给「试新工艺」留炉次、留几炉）；调度员（先烘谁家的、算法要不要用在这么小的问题上）。
10. **哪一步最可能错？** ① 把 UCB 公式里的 c 当常数照抄（本讲实测 c=1 比贪心差两倍）；
    ② 用「多跑几次取中位数」掩盖 UCT 的系统偏差（本讲 UCT 是**系统性**偏向规整解）；
    ③ 把深度变化的 UCT 的模拟值加总（根节点也被算成一条模拟、越深的节点模拟值越小）。

## 实跑数字（全部来自 `day70_result.json`，300 次重复）

### 一、bandit：谁在为「试」付钱
| 策略 | 平均 regret | 最差 10% | 冠军工艺拉动 |
|---|---|---|---|
| 纯贪心（只热身一次） | 21.1 | 49.1 | 230 |
| ε-贪心 ε=0.1 | **13.7** | 27.8 | 314 |
| UCB c=1（教材默认） | 45.1 | 50.8 | 139 |
| UCB c=0.25（调过） | 16.3 | 35.8 | 277 |
| Thompson（Beta 后验） | 22.6 | 36.2 | 241 |
| UCB c=0.25 · 三强贴身 | 18.2 | 37.2 | 242 |
| 纯贪心 · 三强贴身 | 22.8 | 48.0 | 193 |

三条教学点：

- **c 不是常数**。c=1 → 45 炉、c=0.25 → 16 炉，**同一个算法差了 2.8 倍**，而它只改了一个数。教材那句「c 可以取 1」是给「T 无穷大」的渐近说法，赛季只有 400 炉。
- **一个冠军 vs 三强贴身**：纯贪心在「三强贴身」上开始崩（单条轨迹里 392 炉全押在 0.38 的「带杆密集烤」上——它第一次碰巧烤成了），
  因为**第一次观测太薄**。这就是「只热身一次」的代价。
- **Thompson 的价值不在均值，在尾部**：作为 Bernoulli 问题，它的均值并不比调好 c 的 UCB 好（22.6 vs 16.3，这是本实例的如实结果），但它**不需要调参**，且在先验与真值偏离时更稳。

### 二、UCT 排产：精确 DP 是 700.6 担·天
| 方法 | 成本 | gap |
|---|---|---|
| 精确 DP（81 状态，全枚举 2520 种核对） | **700.6** | — |
| 静态规则：最短批优先 | 711.4 | +1.5% |
| 静态规则：担数/时长比 | 713.0 | +1.8% |
| 静态规则：最大批优先 | 819.4 | +17.0% |
| UCT 1000 次（访问最多选枝） | 428.7 | **−38.8%** |
| UCT 1000 次（均值最好选枝） | 287.7 | **−58.9%** |

**最优方案**：老周 → 德生 → 德生 → 老周 → 小陶 → 阿兰 → 阿兰 → 小陶。注意它并不是「一家连烘完」，而是**两家交错**（老周第一批、德生两批、老周第二批）。

- 🔴 **本讲核心：UCT 不会逼近最优，它逼近的是「规整解」**。模拟次数从 10 → 1000，成本从 29 → 429（访问口径）
  **单调变差**。原因是所有叶子都从「当前节点」重新计时，**树越深、模拟值越小**，于是搜索被「把剩余批次全塞给一户连着烘」这类规整路径吸引——它不是噪声，是**系统偏差**，取中位数掩盖不了。
- **选枝口径比模拟量更值钱**：同样 1000 次，「均值最好」比「访问最多」好 33%（287.7 vs 428.7）。UCT 经典的「取访问最多的孩子」在本问题上是**错读**——访问多只说明它探索得多。
- **rollout 设计几乎无关胜败**：规则 rollout 302.6 vs 随机 rollout 295.1（300 次模拟），差 2.5%，被种子方差吃掉。**小树上，rollout 不是第一矛盾。**
- **真正的结论**：4 户 8 批 = 2520 种序列、81 个 DP 状态——**这题不需要 UCT**。UCT 该用在「深度到不了底、分支大、且能自适应」的问题上（AlphaGo 那类），
  而不是这里的「两维状态、一眼穷尽的排产」。**算法选型的第一步是先把问题规模量一遍**（Day21/26 的老规矩）。

## 本讲的坑（全部实跑暴露，按发现顺序）

1. **`pol_ucb1` 里 `c=1` 直接抄书**：第一版只跑 200 次重复，结论是「UCB 最差」，我以为是自己写错了，查了三遍公式，
   后来把 c 扫了一遍才发现**是这个实例上 c=1 真的过量探索**（每轮 log T 增长，而 T=400 时 log T≈6，噪声项 ≈ 2.4·√(6/n)）。
   → 结论保留，但必须把「c 不是常数」写进教案，而不是悄悄换成 0.25 了事。
2. **UCT 的根节点被当成一条模拟**：`path = [root]`，根 N=1 与子节点 N=1 同时出现，
   「访问最多」永远判给第一个孩子 → 输出 0.0 担·天这种一眼假的数。**修复：模拟必须从「刚展开节点的下一步」开始**（`rollout(st)` 不包含 st 本身）。
3. **深度变化的模拟值不能直接加总**：节点越深，`evaluate(seq, t0)` 的 t0 越大，值必然越小。
   第一版直接用「累计负成本」当 Q，导致**越深越被偏爱**，正好与正确方向相反。修法：rollout 必须返回「整条路径的累计等待」（含已经付出的部分）。
4. **旧 / 新状态对象串号**：新建子节点时写成了从 `root.state` 派生（而不是父节点），
   子节点的 `untried` 与父节点重复 → 同一个批次被排两次、序列长度 6 但成本算成 183（不可能的小数）。**断言「序列长度 = 8」救回**。
5. **把「UCT」写成「每步重建一棵树、且不继承」**：程序能跑，但每一步都从零学，等于把最优解反复忘掉。
   实测「每步重建」在 100 次模拟下 794.7，而「一次建树、逐层下棋」在 100 次模拟下 244.0——**同名的算法，两种写法差 3 倍**。
6. **`np.median` 骗人**：前几版用「5 个种子的中位数」报 UCT，结果 100 次模拟的中位数居然是 174（看似不错），
   而均值是 244、最差 302.8。**中位数会把「成功的少数」放大**，本节全部改为**均值 + 最好 + 最差**三栏。
7. **`json.dump` 遇 `np.float64` 崩**（Day66 家族），统一 `round(float(...), 3)`。
8. **中文图零告警**（Noto Sans CJK SC），`-W error` 全程无告警。

## 和前面几讲怎么接

- **Day18（MDP 值迭代）**：值迭代要求 $P(s'\mid s,a)$ 已知；本讲 bandit 是「$P$ 未知、边学边用」。
  两讲的共同语言是 regret：值迭代的误差是**数值误差**，bandit 的 regret 是**信息的价格**。
- **Day16 / Day56 / Day66（DP）**：第二部分的 81 状态 DP 就是同一套「状态 = 每家烘了几批」的转移，
  只是本讲的 DP 用来**校验 UCT 的下界**（而不是求解本身）。
- **Day42 / Day47（禁忌搜索 / 流水车间）**：静态规则「担数大、批时短先上」其实是 Day47 NEH 的老经验；
  本讲说明：**在 8 个批次的规模上，规则的 1.5% 差距比 UCT 的 40% 差距更值得信。**
- **Day61 / Day68（调度）**：本讲的「分批连续作业 + 户内先后」是 Day68 区间调度的一个特例，
  下次可接「每户 3~4 批」——那才是 UCT 有意义的规模（此时 DP 状态 4^4~5^4 仍可算，先量规模再决定算法）。
